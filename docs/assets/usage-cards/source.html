02 / 任务路由

简单任务轻量走，困难任务进证据流

Coordinator 先判断任务难度和风险，Reviewer 复核是否过松，再决定走普通路径、软证据路径或严格证据路径。

自适应流程
用户问题question
→
Coordinator难度 / 风险 / 证据策略
→
Reviewer复核过松判断
→
Planner生成执行计划

简单问题

身份、闲聊、低风险说明。

  • 不强制检索
  • 快速回答
  • 保留短期上下文

中等问题

技术解释、方案比较、有限事实判断。

  • 允许软证据
  • 证据不足可受限输出
  • 在 telemetry 标记不足

困难 / 高风险问题

学术、事实、高风险决策、当前信息。

  • 必须尽力检索证据
  • Critic 审计关键 claim
  • Gate 可打回或拒绝

意义：不靠用户手动触发证据系统，而是让 Agent 自主判断复杂度；Reviewer 是第二道保险，避免所有任务都被误判为“简单”。

看 UI：路由/审查 Tab关键字段：difficulty / workflow / confidence / reviewer.findings
03 / 默认工作流

不是死链，而是带回路的状态图

证据不足、门禁阻断、验证失败时，工作流会回到检索或推理阶段，而不是硬着头皮输出。

Workflow Spec

计划plan

推理reason

响应respond
主流程 回路/重试 checkpoint: retrieve / audit / gate / verify / consolidate

04 / 结构化交付

节点之间不传散文，传可审计 payload

每个节点都有设计时契约和运行时产物。这样下游 Agent、Reviewer 和 Gate 才能稳定检查具体字段。

Handoff Contract

设计时契约

input_contract上游必须交付什么
output_contract下游可以依赖什么
work节点实际负责什么
gate_policy节点级风险/审批规则

运行时产物

actual_input本轮真实收到的数据
actual_output本轮真实产出的数据
process可审计过程摘要
handoff传给下游的结构包

为什么要这样做

  • 能定位失败发生在哪一层
  • 能替换单个 Agent 或节点
  • Gate 可以检查证据数量和风险
  • UI 能展示真实输入输出
Planner输出计划 + 证据策略
→

handoff

{ query, risk_level, required_evidence, route }

→
Retriever按契约检索证据
看 UI：点击工作流节点或连线关键字段：actual_input / actual_output / process / handoff
05 / RAG 与证据

知识库先召回，再变成可引用证据

本地知识库负责找材料，证据系统负责把材料变成带来源、span、hash、score 的 EvidenceItem。

BM25 + Semantic + Graph + Wiki
knowledge/md / txt / json
→
Ingest扫描 + 切 chunk
→
Retrieve多方法召回
→
Evidencesource / span / hash
→
Gate合格才放行

本地检索

  • BM25: 精确术语
  • 语义: 近义/跨语言
  • Graph: 概念关系扩展

Fallback

  • Wiki 可手动或低分触发
  • 外部来源会写 diagnostics
  • 失败不静默吞掉

证据栏展示

  • 参考文献索引
  • confidence 和 locator
  • 合格/不合格证据

使用方式：在 RAG Tab 输入查询，切换 BM25、语义、Graph、Wiki；用 score_breakdown 判断哪种检索有效。

看 UI：RAG Tab + 证据 Tab命令：python -m reasoning_agent_template rag-eval --cases configs/rag_benchmark_cases.json
06 / 记忆边界

短期记忆、长期记忆、知识库必须分开

这三类数据会影响 Agent 的方式不同；混在一起会造成污染、误召回和不可审计。

Memory Gate

短期记忆

当前 thread 对话上下文。

  • 自动记录
  • 按 thread 隔离
  • 不进入知识库

长期记忆

用户偏好、项目事实、流程经验。

  • 分区保存
  • 需要证据
  • 需要 write_memory gate

知识库

论文、文档、规范、API、数据集。

  • 放入 knowledge/
  • 通过 RAG 召回
  • 不代表用户偏好
Verify输出验证完成
→
Consolidate生成沉淀候选
→

Proposal only

只生成候选，不直接改长期记忆或技能。

→
Gate人工/证据审查
看 UI：记忆 Tab关键边界：short_term ≠ long_term ≠ knowledge_base

08 / 二次开发闭环

从需求到可验证 Agent 的开发流程

不要一上来写大段 prompt。先定义边界、数据、节点、门禁和测试，再让 Agent 在可观测工作流里运行。

Developer Loop

1定义目标

identity、失败边界、受众和任务风险。

2准备知识

把论文、规范、API 文档放进 knowledge/。

3设计角色

Agent spec 写职责、工具、权限、记忆访问。

4设计流程

Workflow spec 写节点、边、contract、gate。

5补技能

把强约束写入 skills/*/SKILL.md。

6跑测试

python -m unittest discover -s tests -v

7测召回

rag-eval --cases configs/rag_benchmark_cases.json

8开调试台

看状态、节点、证据、门禁、事件和 raw JSON。

开发判断：新增能力时先问它是 Agent、节点、工具、技能、记忆策略还是 RAG 方法；不要把所有东西都塞进一个大 prompt。

看文档：docs/user-manual.md最小验证：unittest + node --check + rag-eval
